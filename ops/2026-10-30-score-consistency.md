# AUDIT-10 점수·순위·해결자 집계

사용자는 남은 AUDIT별로 질문하지 않고 순차 구현/검증하도록 위임했다. 화면의 `명`/Solvers 의미와 기존 첫 정답 정책을 기준으로 문제의 solved_count는 **일반·대회를 합친 문제별 고유 해결자 수**, 참가자 점수는 **대회 문제당 첫 정답만**으로 정했다. 과거 통계값을 자동 보정하지 않는다.

## 변경과 이유

- Spring 대회 제출의 최초 참가자 조회부터 `PESSIMISTIC_WRITE`로 잠근다. Python의 기존 참가자 FOR UPDATE와 같은 행이므로 같은 참가자의 객관식·실습·코딩 점수가 직렬화된다. 첫 정답 조회는 잠금 이후이며 점수·제출 결과는 같은 트랜잭션이다. 점수 저장을 flush한 뒤 순위를 조회한다. 일반 관리 변경이 오래된 score를 덮지 않도록 참가자 엔티티는 DynamicUpdate를 사용한다.
- 순위는 Redis가 아닌 DB의 확정 상태로 읽는다. 점수 내림차순 → 마지막 해결 시각 오름차순(NULL 마지막) → 사용자 ID 오름차순의 순번이다. 차단 참가자는 순위에서 제외한다. 즉시 결과/코딩 상태/순위표가 같은 순서를 사용하며 순위표와 코딩 상태의 복수 조회는 REPEATABLE_READ다. Spring 점수 시각은 DB UTC clock, Python도 DB UTC clock을 사용한다.
- 이전 ZSet은 읽지도 갱신하지 않는다. Python의 기존 알림 hook은 테스트/호출 호환성을 위한 no-op이며 외부 Redis 쓰기는 없다. 오래된 캐시·늦은 갱신으로 보이는 순위가 되돌아가는 문제를 제거했다. Redis는 기존 제출 cooldown 등 다른 용도로 유지한다. DB 순위 조회량 증가는 운영 실행계획/부하 점검 대상이다.
- `problem_solver(prob_id,user_id)` 고유 키로 최초 해결자만 기록하고, 같은 트랜잭션의 CTE로 성공적으로 추가된 경우만 solved_count를 증가시킨다. Java 일반/대회 및 로컬 코딩 mock, Python 채점기가 동일한 계약을 사용한다. 재전달·동시 정답·일반과 대회 교차 제출도 중복 집계를 막는다.
- 대회 문제별 조회도 DISTINCT user로 계산한다. 프론트의 고정 분모 128 가짜 비율은 없애고 실제 해결자 수와 제출 수를 표시한다. 개인 티어의 기존 첫 일반 정답 갱신은 유지한다.

## 검증

Java 모의 선택 회귀 191개(신규 점수/순위 7+기존 184) 통과. 실제 VM DB 테스트 6개는 미기동으로 건너뜀. Python 신규 점수 계약 mock 3개·기존 조정기 mock 5개 통과. 프론트 기존 76개와 TypeScript 검증. 서버·DB·Docker 기동 없음.

Python PostgreSQL 회귀 파일에 같은 사용자 재정답, 다른 사용자, **Java의 실제 CTE SQL과 Python 완료 처리 동시 실행** 3개를 추가했다. 이번에는 기동하지 않았으며 기존 32+신규 3=35개 실제 DB 검증은 별도 승인 대상이다. 이 검사는 SQL 계약의 동시성이며 Spring JPA 참가자 잠금의 실제 혼합 실행을 대체하지 않는다. 실제 JPA·SQL 마이그레이션·혼합 경로 부하 및 순위 조회 비용은 운영 전 검증이 남았다.

## 운영 실행·복구안 — 미실행

1. 별도 승인 후 모든 결과 writer/API·채점 dispatch를 일시 정지하고 운영 DB 백업·현재 버전/digest를 보관한다. 참가자 (contest_id,user_id) 유일성과 existing score/time 데이터를 읽기로 확인한다.
2. `2026-10-30-score-consistency.sql`로 solver 테이블을 만들고 일반/대회 기존 정답 이력에서 중복 방지 키만 채운다. SQL의 foreign key와 실제 schema/column을 대조한다. 기존 solved_count는 변경하지 않고 불일치 보고서를 보존한다. 과거 통계/점수/시각 보정은 별도 검토·승인 대상이다.
3. Java·Python writer와 DB 순위 reader를 함께 전환한다. 구버전 Python/Java가 계속 기존 카운터를 쓰는 혼합 운영을 허용하지 않는다. 최신 프론트도 함께 연결한다. 실제 혼합 제출, 같은 문제 동시 정답, 다른 문제 점수 누락, 롤백/재시도, 오래된 Redis·동률·차단·0점 참가자를 검증한다.
4. 순위 DB 조회 인덱스/계획을 확인하고 필요하면 `(contest_id, score DESC, last_solved_at, user_id)` 인덱스 추가안을 별도 승인한다. 과거 캐시는 즉시 삭제할 필요가 없으며 데이터 purge는 하지 않는다.
5. 실패하면 제출/채점 쓰기를 닫은 상태에서 호환 버전으로 복구한다. solver 테이블·확정 결과를 삭제하거나 확정 점수를 되돌리지 않는다. 구 writer로 복귀 시 ledger/counter 일관성이 달라지므로 재개 전에 검토한다. AUDIT-01의 구 격리 없는 채점기를 다시 열지 않는다.

운영 미배포·push 없음. AUDIT-01 P0·Terraform 보류 유지.
