# AUDIT-06 대회 제출 보드

## 문제와 변경

대회 실습·객관식은 contest_submission에 완료 결과를 저장하지만 화면은 solve_submission 기반의 일반 보드를 읽었다. 대회 실습 제출 번호를 일반 문제 pending_sub 키에 넣고 결과 링크에서도 서로 다른 ID를 혼용하여, 실제 채점과 화면 결과가 어긋났다.

새 GET `/api/contests/{contestId}/problems/{contestProblemId}/board?page=1&size=50`은 대회·대회 문제·로그인 사용자로 조회한다. 기본 페이지 크기는 50, 상한은 100이며 최신 제출 시각·ID 내림차순이다. 모든 상태를 포함해 대기·완료·실패를 새로고침 후에도 확인한다. Cache-Control: no-store를 반환하고 새 경로를 기존 공개 GET 규칙 앞에서 authenticated로 지정한다.

응답:
- contestId, contestProblemId, probId, page, totalPages, total
- currentTotalScore: 현재 참가자의 대회 전체 총점. 각 제출이 획득한 점수로 해석하지 않는다.
- submissions: submissionId(항상 대회 제출 ID), solveSubmissionId(코딩 상세 연결만), submissionStatus, isCorrect, submittedAt, nickname, language, runtime, memoryUsage

대회 시작 전, 비참가자·차단된 참가자, 잘못된 대회/문제 쌍은 거절한다. 종료 후에는 기존 참가자의 조회를 허용하고 AUDIT-05의 문제 공개 범위 검사를 다시 수행한다. 목록과 총점을 REPEATABLE_READ 트랜잭션으로 읽어 한 응답에서 서로 다른 확정 시점의 데이터를 섞지 않는다. 실제 PostgreSQL 스냅샷/실행 계획 검증은 이번 모의 테스트 범위 밖이다.

**사용자 확정 정책:** 대회·문제별 본인 제출 결과와 현재 총점만 표시한다. 사용자가 본인 제출 전용 정책을 선택했다. 다른 참가자 비교는 기존 순위표에서 수행한다. 모든 유형은 대회 제출 번호를 사용하고 코딩 상세 링크만 별도 일반 제출 번호를 사용한다.

프론트는 일반 보드·일반 pending_sub 키를 사용하지 않고 대회 보드를 읽는다. 객관식/실습은 즉시 완료 응답을 표시한다. 객관식은 선택한 답안 배열을 그대로 전송하고 보드를 갱신한다. 코딩만 대회 보드에 PENDING/JUDGING이 있을 때 다시 조회하며 COMPLETED/FAILED에서 멈춘다. 화면을 떠나면 요청을 취소하고 늦은 응답을 무시한다. 조회 실패는 오류로 표시하며 일시 장애는 재시도한다. 페이지 이동·새로고침·대회 총점 표시를 추가했다.

코딩 코드/OBO 링크는 명시적인 solveSubmissionId만 사용한다. 대회 객관식은 일반 SolveSubmission/선택 답안을 저장하지 않으므로 일반 OBO 결과 링크를 생성하지 않는다. 기존 데이터의 답안을 추정하거나 일반 제출 행을 새로 만들어 이관하지 않는다. 그 상세 해설 연결은 별도 저장 계약이 필요하다.

## 검증 범위

최종 검증: Java 선택 회귀 129개 통과(신규 보드 서비스 17 + HTTP/인증 3 + 기존 109), 실패/오류 0. 기존 VM PostgreSQL 테스트 6개는 이번에 재기동하지 않아 건너뛰었으며 이전 승인 실행의 통과 기록은 유지한다. 프론트 76개(신규 21 + 기존 55), TypeScript --noEmit, staged diff 공백 검사를 통과했다.

Java 서비스·MockMvc 테스트와 프론트 Vitest/TypeScript로 대회/문제/사용자 범위, 시간/차단 경계, 세 유형 결과, 완료·실패, 번호 혼용, 재조회·폴링·화면 종료 처리를 검사한다. DB·Redis·AWS는 모의 처리하며 실제 서버 포트를 열지 않는다. 실제 JPA 쿼리·운영 데이터·브라우저/전체 채점 통합은 미검증이다. VM PostgreSQL 검증 승인을 이번 DB 기동에 확대하지 않는다.

첫 HTTP 테스트에서 기존 `/api/contests/**` 공개 규칙에 새 보드가 들어가는 문제가 드러났다. 보드 전용 인증 matcher와 무인증/위조 토큰 회귀를 추가했다. 이는 수정 전 실패 기록이며 최종 테스트 결과와 구분한다.

## 운영 실행·복구안 — 미실행 / 별도 승인

1. 확정된 본인 제출 정책과 운영 데이터의 contest_submission → contest_problem → solve_submission 연결을 대조한다. 기존 API/프론트 버전을 보존하고 새 API·프론트를 함께 전환할 실행 대상을 승인받는다. DB 스키마 변경은 없다.
2. 백엔드를 먼저 반영하고 테스트 참가자로 세 유형 제출·결과·현재 총점·실패·새로고침·다른 대회 ID·차단 참가자·무인증 요청을 확인한다. 실제 DB 쿼리와 스냅샷 격리, 페이지 성능도 확인한다.
3. 프론트를 반영해 일반 제출 섞임과 잘못된 링크가 사라졌는지, VM 정확한 세션 종료와 터미널 인증이 유지되는지 검증한다. 운영 DB/AWS/서버 기동·배포·push는 별도 승인 없이는 실행하지 않는다.
4. 문제가 생기면 대회 제출 결과 화면을 닫고 호환되는 API·프론트 조합으로 복구한다. 새 프론트가 새 API 없이 배포된 상태를 유지하거나 일반 보드로 자동 대체하지 않는다. 데이터 삭제/과거 결과 재작성은 없다.

AUDIT-01 P0 최우선 미해결·Terraform 보류는 유지한다. AUDIT-10의 점수 동시성/Redis 갱신 정책을 이번 조회 수정으로 해결했다고 보지 않는다.
